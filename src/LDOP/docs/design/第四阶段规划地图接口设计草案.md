# 第四阶段规划地图接口设计草案

更新时间：2026-05-21

这份文档从早期“UFOMap 接口备忘”升级为 LDOP 第四阶段的 planner-facing 接口草案。它的目的不是创新一种新的规划地图算法，而是把 LDOP 已经具备的静态地图、动态目标预测和风险证据整理成无人机规划算法开发者可以直接消费、实现和验证的通用契约。

第四阶段的成功标准不是“发布了更多地图 topic”，而是外部规划器能稳定、批量、可解释地回答这些问题：

- 某个候选位置现在能不能去。
- 某段轨迹边是否碰到静态障碍、未知区或膨胀障碍。
- 未来某个时间点，动态目标预测是否会让该位置或轨迹段变危险。
- 局部规划范围内有哪些静态障碍、未知体素、动态风险点或距离场值。
- 如果查询结果不安全，具体是由哪一层、哪个时间、哪个目标或哪类地图状态触发。

## 设计定位

LDOP 第四阶段应定位为“动态环境感知到规划查询之间的通用适配层”，而不是一个绑定特定规划器的 cost function 或完整 planner。无人机规划算法开发者常见的消费方式不同：采样/搜索类规划器需要大量点和线段碰撞检查，轨迹优化和 MPC 需要距离、风险和可选梯度，学习型或评估型方法需要局部地图快照、动态目标风险和可复现实验输入。因此，LDOP 应优先提供分层、批量、可调策略的查询结果，让不同规划器自己决定如何使用这些结果。

第一版主路径应学习 `ROG-Map` 的“内部地图 + 高频查询接口”形态；地图共享和 RViz 可视化只作为辅助路径。换句话说：

- 规划主路径：高频、批量、低开销的查询接口。
- 调试路径：返回触发原因和最近一次查询证据，配合 RViz marker 检查 planner-facing 结果。
- 可视化路径：低频发布点云或 marker，用来观察静态膨胀层、动态风险层和 query debug。
- 地图共享路径：如果后续确实需要完整本地地图副本，再补 `/ldop/ufomap` 或等价序列化输出。

第四阶段必须继续保持静态层和动态层可分离。静态层来自第一阶段维护的 UFOMap 静态证据；动态层来自第三阶段 `/ldop/dynamic_object_predictions`。动态风险可以参与 planning map / risk map 融合，但不应永久写入 UFOMap 静态地图。

## 非目标

为了保持通用性，第四阶段第一版不应把范围扩散成下面这些目标：

- 不实现新的 motion planner，也不把某个规划器的代价函数固化为 LDOP 唯一语义。
- 不要求规划器直接访问 `UfomapMapper::runtime.map` 或依赖 UFOMap 内部类型。
- 不把 RViz 点云或 marker 当作规划主接口。
- 不把动态目标预测写回静态地图，也不从 UFOMap dynamic candidate 反推未来动态风险。
- 不在第一版强制实现完整 ESDF、完整 UFOMap 发布或同进程共享地图。
- 不把 `seenFree()` 简化成 planner-facing `FREE`。`seenFree()` 是 DUFOMap 动静态判别证据，规划语义里的 known free 需要独立定义。

## 当前 LDOP 基础

当前 LDOP 已经具备第四阶段的核心输入：

- 第一阶段已经维护 UFOMap，并输出当前帧 `/ldop/static_cloud`、`/ldop/dynamic_cloud` 和 `/ldop/static_map_markers`。
- 第二阶段已经输出稳定动态目标 `/ldop/dynamic_objects`。
- 第三阶段已经输出 `/ldop/dynamic_object_predictions`，其中每个目标包含多分支 `branches`、分支概率 `probability`、未来采样 `time_from_start`、模型原生预测状态/协方差和 `influence_weight`。
- `UfomapMapper` 已有内部查询能力：`queryNode()`、`seenFree()`、`queryLocalOccupied()`、`queryNearestOccupied()`、`queryDynamicCandidates()`。
- `queryNode()` 已返回 `UfomapOccupancyState::{Unknown, Free, Occupied, OutOfMap}`，`PredictionMapNodeQuery` 也保留同等状态语义。这是 planner-facing 状态查询的底层基础，但还不是最终 ROS service/msg 契约。
- `queryLocalOccupied()` 和 `queryNearestOccupied()` 已支持查询深度控制，第三阶段通过 `prediction_map_query_depth` 暴露了 coarse/fine 查询开关，后续第四阶段可以直接复用这个性能调节入口。
- `Ldop` 已经用 `UfomapPredictionMapQuery` 把 UFOMap 查询注入预测器，说明“只读地图 adapter”这个边界已经跑通。

当前缺口也很清楚：

- 仓库当前没有 `srv/` 目录，规划器还没有稳定 ROS service 接口。
- 当前依赖里没有 `ufomap_msgs` / `ufomap_ros`，所以 `/ldop/ufomap` 不能作为第一版实现的默认前提。
- planner-facing `FREE`、`UNKNOWN`、`OCCUPIED`、`INFLATED_OCCUPIED`、`OUT_OF_MAP` 还没有稳定消息语义；其中除 `INFLATED_OCCUPIED` 以外的四类底层状态已有基础查询，`INFLATED_OCCUPIED` 和 unknown 策略仍需第四阶段定义。
- 批量点/box 查询、线段碰撞检查、局部 planning map、完整地图副本或 ESDF 仍未实现，这些要等第四阶段 planner-facing 接口开始后落地。
- 动态预测已经保留分支概率、协方差和 `influence_weight`，但还没有被整理成按时间查询的连续风险层。

### UFOMap 应用层借鉴点归属

本次把 UFOMap 主分支应用层中最值得借鉴的核心点按当前落地边界重新归类。调试/运维类 `clear/reset/save snapshot` 和 diagnostics/status/timing 不列为核心借鉴点；必要的时间戳、截断标志和触发原因仍保留在 service response 设计中。

| 编号 | 借鉴点 | 当前 LDOP 归属 | 文档/实现边界 |
|---|---|---|---|
| 1 | 显式 `UNKNOWN/FREE/OCCUPIED/OUT_OF_MAP` 点状态 | 已实现，属于“现在打基础，P4 继续收益” | `UfomapMapper::queryNode()` 和 `PredictionMapNodeQuery` 已具备底层状态语义；P4 继续把它包装成稳定 planner-facing service/msg |
| 2 | `BoundingVolume-lite` 几何查询抽象 | P4 planner-facing 落地 | 从当前 sphere-only 查询扩展到 LDOP 自己的 AABB、sphere、line、ray、OBB/frustum 或 corridor 轻量消息；不暴露 UFOMap 类型 |
| 3 | coarse/fine 查询深度控制 | 已实现，属于“现在打基础，P4 继续收益” | `prediction_map_query_depth` 已接入 P3 地图交互，P4 批量查询和局部地图接口可复用 |
| 4 | bounded nearest search / 最近障碍证据 | 已实现，属于“现在打基础，P4 继续收益” | `queryNearestOccupied()` 已提供局部最近障碍近似；P4 可以扩展为 nearest occupied / unknown / trigger voxel，真正需要连续距离/梯度时再升级 ESDF |
| 5 | swept-volume 辅助线段检查 | P4-B planner-facing 落地 | 第一版保留采样法；后续用 line segment + robot radius 近似成 OBB、capsule 或 AABB 序列，降低薄障碍漏检和采样步长敏感性 |
| 6 | 完整/局部地图发布、depth、compression、full snapshot | P4-E 后置增强 | 第一版不依赖 `/ldop/ufomap`；后续如需地图副本，借鉴局部 bounding volume + depth + compression + 新订阅者 full snapshot 语义，避免每帧全量发布 |

## 外部经验取舍

`ROG-Map` 值得借鉴的是 planner-facing 能力形态，而不是必须照搬数据结构或 ROS topic 名。典型能力包括：

- `isOccupied(pos)` / `isUnknown(pos)` / `isKnownFree(pos)`：点状态查询。
- `isOccupiedInflate(pos)` / `isUnknownInflate(pos)` / `isKnownFreeInflate(pos)`：膨胀层查询。
- `isLineFree(start, end, ...)`：轨迹边碰撞检查。
- `boxSearch(...)` / `boxSearchInflate(...)`：局部范围障碍查询。
- `getDistance(pos)` / `updateESDF3D(...)`：ESDF 查询和更新。

Voxblox、FIESTA 一类 ESDF 工作说明距离场和梯度对 MAV 局部规划很常见；EGO-Planner 一类 ESDF-free 工作则说明不是所有规划器都愿意为 ESDF 付出更新代价。LDOP 第一版因此不应强制 ESDF，但应在接口中预留 `distance`、`nearest_obstacle` 和后续 `gradient` 的位置。

OctoMap / UFOMap 的经验说明三维地图里 `free / unknown / occupied` 的语义很重要，不能只发布 occupied 点云。MADER 等动态环境规划工作则说明动态障碍应进入时间化约束或风险评估，而不是污染静态地图。LDOP 的优势正好在于已经把静态层、动态目标跟踪和短时预测分开，因此第四阶段应把这种分层保留下来。

## Planner 适配视角

第一版接口需要覆盖三类常见消费者：

| 规划器类型 | 主要需求 | LDOP 应提供的最小能力 |
|---|---|---|
| 采样 / 搜索规划器 | 批量点有效性、边有效性、首个碰撞点 | `/ldop/query_planning_points`、`/ldop/check_planning_lines` |
| 轨迹优化 / MPC | 静态距离、动态风险、可选最近障碍或梯度 | 点查询中的 `distance` 预留、动态风险和后续 `/ldop/query_esdf` |
| 学习 / 评估 / 调试工具 | 局部障碍、风险点、查询证据和可复现输入 | `/ldop/query_local_planning_map`、debug marker、触发原因字段 |

这个表的含义是：LDOP 不需要猜测下游算法会怎么规划，只需要把安全性和风险证据整理成稳定接口。不同规划器可以把 dynamic risk 当作硬约束、软约束、代价项、训练标签或评估指标。

## 接口设计原则

第一版应遵循这些原则：

- 批量优先：规划器不能对每个采样点单独调用 ROS service；点、线段和局部地图都应批量查询。
- 分层返回：response 同时保留静态层、动态层和融合摘要，避免只给一个 `safe` 布尔值。
- 策略显式：unknown 策略、膨胀半径、动态风险阈值、是否包含动态层都由请求字段或参数明确控制。
- 调试可解释：不安全结果必须能说明触发原因，至少能定位到静态状态、动态目标、风险时间和查询采样点。
- 内部可替换：UFOMap 是当前静态底座，但规划器只依赖 LDOP 的 `.srv` / `.msg` 语义，不依赖 UFOMap 类型。
- 时间语义明确：动态风险查询基于 prediction message 的 `header.stamp + time_from_start`，不把当前帧动态点云误当未来风险。
- 低耦合扩展：ESDF、完整地图副本和同进程 API 都是增强路径，不阻塞第一版通用查询接口落地。

## 推荐的第四阶段内部模块

建议新增一个独立 planner-facing 层，而不是继续把逻辑塞进 `Ldop` 或 `UfomapMapper`：

```cpp
class PlanningMapQuery {
 public:
  PlanningPointBatchResult queryPoints(const PlanningPointBatchQuery& query) const;
  PlanningLineBatchResult checkLines(const PlanningLineBatchQuery& query) const;
  PlanningLocalMapResult queryLocalMap(const PlanningLocalMapQuery& query) const;
  PlanningRiskResult queryDynamicRisk(const PlanningRiskQuery& query) const;
};
```

这个模块只组合已有数据源：

- 静态层读取 `UfomapMapper`，负责 occupied / unknown / inflation / local obstacle / line check。
- 动态层读取最近一帧 `DynamicObjectPredictionArray` 快照，负责按未来时间查询动态风险。
- 融合层输出 planner-facing 风险摘要，但不修改 UFOMap 静态地图。

`Ldop` 继续负责 ROS I/O、线程调度、发布和 service 注册；`UfomapMapper` 继续负责 UFOMap 插入、基础节点查询和读写锁；预测器继续只发布预测，不直接知道规划器接口。

### 线程与快照边界

service 回调不应长时间持有 UFOMap 读锁。静态层查询可以先按批量请求组织查询范围，在 `UfomapMapper` 内部一次读锁完成必要查询，再把中间结果交给 `PlanningMapQuery` 做风险和融合计算。动态层应缓存最近一帧 `DynamicObjectPredictionArray` 的轻量快照，避免 service 查询时反向阻塞 predictor 或 tracker。

地图更新和规划查询时间戳可能不同。response 应返回实际使用的 `map_stamp`、`prediction_stamp` 和 `query_stamp`，让规划器判断结果新鲜度。第一版可以先用最近快照，后续再补时间同步或多帧预测缓存。

## 推荐 ROS 接口

第一版建议先做三个批量 service，而不是先做完整地图发布。

### `/ldop/query_planning_points`

用途：批量查询候选点是否安全，适合采样点有效性检查、轨迹优化采样点代价查询和局部调试。

请求建议包含：

- `std_msgs/Header header`
- `geometry_msgs/Point[] points`
- `duration[] time_from_start`：为空表示只查静态层；长度为 1 表示所有点共用同一个未来时间；长度等于 `points` 表示逐点时间。
- `float64 robot_radius`：无人机等效安全半径。
- `float64 static_inflation_radius`：静态障碍额外膨胀半径；若为 0，则只使用 `robot_radius`。
- `bool treat_unknown_as_occupied`
- `bool include_dynamic_risk`
- `float64 dynamic_risk_threshold`
- `bool request_debug_info`

响应建议包含：

- 每个点的静态状态：`FREE` / `UNKNOWN` / `OCCUPIED` / `INFLATED_OCCUPIED` / `OUT_OF_MAP`。
- 每个点的 `seen_free_evidence`，仅作为 DUFOMap 证据，不等同于规划 free。
- 每个点的 `static_risk`、`dynamic_risk`、`combined_risk` 和最终 `safe`。
- 可选 `nearest_obstacle_distance`，第一版没有 ESDF 时可返回最近局部 occupied 的近似距离或不可用标志。
- 可选 `trigger_reason`：`NONE` / `STATIC_OCCUPIED` / `STATIC_INFLATED` / `UNKNOWN` / `OUT_OF_MAP` / `DYNAMIC_RISK`。
- 可选动态证据：触发风险的 `object_id`、`branch_index`、`branch_probability`、`risk_time_from_start` 和风险中心点。

### `/ldop/check_planning_lines`

用途：批量检查轨迹边、搜索图边或多段轨迹采样边。第一版可以沿线采样，后续再替换为更高效的 voxel traversal。

请求建议包含：

- `std_msgs/Header header`
- `geometry_msgs/Point[] starts`
- `geometry_msgs/Point[] ends`
- 每条线对应的起止 `time_from_start`，或统一速度假设。
- `float64 robot_radius`
- `float64 static_inflation_radius`
- `float64 max_sample_step`
- `bool treat_unknown_as_occupied`
- `bool include_dynamic_risk`
- `float64 dynamic_risk_threshold`
- `bool request_debug_info`

响应建议包含：

- 每条线是否安全。
- 每条线的最大 `static_risk`、最大 `dynamic_risk` 和最大 `combined_risk`。
- 首个静态碰撞点、未知点或动态风险触发点。
- 触发原因和触发采样序号。
- 最大动态风险对应的目标 `id`、时间和分支概率摘要。
- 可选最近障碍距离，后续接 ESDF 后再补强为更稳定的距离查询。

线段检查的默认采样步长建议为 `min(map_resolution * 0.5, max_sample_step)`。这样第一版实现简单且容易验证；如果后续发现采样法漏检或开销过高，再切换到 3D DDA / voxel traversal。

### `/ldop/query_local_planning_map`

用途：给规划器、学习模块或调试工具一次性取局部范围内的障碍和风险。它不是规划主循环里每个采样点都调用的接口，而是局部环境快照。

请求建议包含：

- `std_msgs/Header header`
- box 或 sphere 查询范围。
- 静态层返回选项：occupied、inflated occupied、unknown、free 是否返回。
- 动态层查询的单个时间或时间序列。
- `float64 robot_radius`
- `float64 static_inflation_radius`
- `bool include_dynamic_risk`
- `uint32 max_static_voxels`
- `uint32 max_dynamic_points`
- `bool request_debug_info`

响应建议包含：

- 静态 occupied / inflated occupied / unknown voxel center。
- 动态风险 voxel 或风险点，包含 `risk`、`time_from_start` 和可选 `object_id`。
- 地图分辨率、frame_id、stamp、查询范围和截断标志。
- 如果结果被截断，应返回 `truncated=true` 和各层原始候选数量，避免规划器误以为局部空间真的很空。

### 后续 `/ldop/query_esdf`

第一版不强制实现 ESDF，但可以先预留后续 service 语义：

- 输入：点数组、是否请求梯度、查询范围或局部 ESDF 版本。
- 输出：每个点的 signed / unsigned distance、可选 gradient、最近障碍点、有效标志。

只有当规划器确实需要梯度优化、本地高频距离查询或更平滑的障碍代价时，再实现该 service。否则 P4-A 到 P4-C 已经足以支持常见采样、搜索和动态风险验证。

## 静态层语义

静态层第一版不必马上构建完整 ESDF，但需要先把状态语义定义清楚：

- `OCCUPIED`：UFOMap 中存在且满足静态占据条件的节点。当前底层 `UfomapOccupancyState::Occupied` 已能表达这个状态。
- `UNKNOWN`：地图中不存在，或没有足够证据判定 free / occupied 的位置。当前底层 `UfomapOccupancyState::Unknown` 已能表达这个状态，但第四阶段仍需要决定 unknown 是否默认触发 unsafe。
- `FREE`：已由 planner-facing 地图证据确认可通行的位置。当前底层 `UfomapOccupancyState::Free` 已能在有 free 证据时返回，但第四阶段 service 仍应把 planner-facing `FREE` 的保守语义写清楚，不能把 `seenFree()` 这种动静态判别证据直接等同为可通行承诺。
- `INFLATED_OCCUPIED`：点本身不一定 occupied，但落入障碍膨胀半径内。
- `OUT_OF_MAP`：超出当前地图可表达范围或查询失败。当前底层 `UfomapOccupancyState::OutOfMap` 已能表达这个状态。

`seen_free_evidence` 应作为单独字段返回，含义是“DUFOMap 动静态判别流程中该点附近存在 seen-free 证据”。它可以帮助调试动静态分割，也可以被下游探索算法参考，但不应被 LDOP 默认合并成 `FREE`。

unknown 策略应由查询参数控制：保守规划可把 unknown 当 occupied；探索或调试可把 unknown 单独返回给上层判断。默认策略建议偏保守，即 unknown 触发 unsafe，但 response 中仍保留 `static_state=UNKNOWN`，避免把 unknown 和 occupied 混成同一种原因。

## 动态风险语义

动态风险来自 `/ldop/dynamic_object_predictions`，不能永久写回 UFOMap。当前 prediction message 已经提供第四阶段需要的核心字段：

- `DynamicObjectPrediction.id`：目标稳定 ID。
- `size`：目标 bbox 尺寸，用于风险半径和可视化。
- `motion_model_type`：解释每个未来点的模型原生状态和协方差。
- `branches[].probability`：trajectory-level GMM 分支概率。
- `points[].time_from_start`：未来采样时间。
- `points[].model_state[0..2]`：未来中心位置。
- `points[].model_covariance`：模型原生协方差，位置协方差由前三维子块派生。
- `points[].influence_weight`：planner/RViz 风险影响权重，不改变模型协方差。

建议第一版按如下思路计算：

- 对每个查询时间 `t`，在每个预测分支里找到最接近 `t` 的预测点，必要时做线性插值。
- 从 `model_state[0..2]` 取动态目标中心。
- 用目标 bbox 尺寸、无人机安全半径、`influence_weight` 和位置协方差派生风险半径。
- 用分支 `probability` 加权，把距离核函数转成 `[0, 1]` 风险。
- 多目标风险第一版建议用 `1 - product(1 - risk_i)` 融合，因为它能表达多个低概率风险叠加后整体风险升高；若为了更保守、可解释和便于调试，也可以提供 `max` 策略作为参数。

动态层输出要保留连续风险值，不要只输出二值碰撞。规划器常常需要区分“必撞”“高风险绕开”“低概率但可接受”这些情况。

### 动态风险调试证据

动态风险一旦超过阈值，response 应尽量返回触发证据：

- `object_id`
- `object_class`
- `branch_index`
- `branch_probability`
- `behavior_type`
- `behavior_value`
- `risk_time_from_start`
- `risk_center`
- `risk_radius`
- `risk_value`

这些字段让 planner 开发者能判断问题来自预测分支本身、风险阈值、目标尺寸、协方差膨胀还是规划器策略。没有这些证据，外部算法只能看到 `safe=false`，很难验证自己的运动规划方法。

## 融合输出语义

规划器最终需要的是融合结果，但调试和算法演进需要分层结果。因此 response 中应同时保留：

- `static_state`
- `seen_free_evidence`
- `static_risk`
- `dynamic_risk`
- `combined_risk`
- `safe`
- `trigger_reason`

推荐默认策略：

- 静态 occupied / inflated occupied 为硬约束，直接 unsafe。
- unknown 是否 unsafe 由请求参数控制，默认偏保守。
- 动态风险默认是软约束，超过阈值才 unsafe；阈值应参数化。
- `combined_risk` 只是默认摘要，不应替代分层结果。
- 如果 line check 中任意采样点 unsafe，则整条线 unsafe，并返回首个触发点；同时返回最大风险点，方便调试“先撞”和“最危险”不是同一点的情况。

第一版 `combined_risk` 可以使用简单、可解释的策略：

- 静态硬约束触发时 `combined_risk = 1.0`。
- unknown 且保守策略开启时 `combined_risk = 1.0`。
- 否则 `combined_risk = max(static_risk, dynamic_risk)` 或 `1 - (1 - static_risk) * (1 - dynamic_risk)`。

具体选择应在实现旁写清楚原因。面向通用规划器时，推荐同时返回分层风险，避免下游被 `combined_risk` 的默认融合策略绑死。

## UFOMap 在第四阶段的位置

UFOMap 仍是 LDOP 的静态地图底座，但第四阶段不应要求规划器直接访问 `UfomapMapper::runtime.map`。独立 ROS 节点之间没有共享内存，规划器无法直接拿到 LDOP 节点内部对象。

实际可行路径有三类：

### 1. LDOP 提供批量查询接口

这是近期主路径。LDOP 继续拥有唯一静态地图语义，规划器通过批量 service 查询点、线段、局部体素和时序风险。

优点：

- 规划包只依赖 `ldop` 的 `.srv` / `.msg`。
- 不暴露 `UfomapMapper` 内部结构。
- 后续 UFOMap 内部实现变化不直接破坏规划包。
- 最容易把动态预测风险和静态地图查询放进同一个响应里。

代价：

- 高频采样规划不能逐点调用 service，必须批量查询。
- service 回调要控制读锁时间，避免阻塞建图线程。
- 非常高频的轨迹优化器可能仍需要本地地图副本或同进程接口。

### 2. 规划器订阅完整地图副本

如果后续引入 `ufomap_msgs/UFOMapStamped` 或自定义序列化消息，可以发布 `/ldop/ufomap`，让规划器本地反序列化并高频查询。

这条路适合非常高频的静态碰撞检查，但当前不是最小可落地路径，因为仓库当前还没有 `ufomap_msgs` 依赖，也没有完整 UFOMap 发布链路。即使后续实现完整地图副本，动态风险仍应保持为独立时间层，不应写入静态地图副本。

### 3. 规划器和 LDOP 同进程

把规划模块和 LDOP 放在同一个进程，通过 C++ 接口直接访问共享地图对象。性能最好，耦合也最高。只有 service 和地图副本都无法满足实时性时再考虑。

## 可视化输出

第四阶段仍应提供 RViz 输出，但它们只用于验证，不作为规划主接口。

建议 topic：

- `/ldop/planning_static_inflated_markers`：静态膨胀障碍可视化。
- `/ldop/planning_dynamic_risk_markers`：按时间切片显示动态风险。
- `/ldop/planning_query_debug_markers`：最近一次 query service 的采样点、碰撞点、未知点和风险点。

如果后续增加 ESDF，可再发布 `/ldop/planning_esdf_cloud` 作为局部可视化切片。

debug marker 应和 service response 使用同一帧 `frame_id`、同一查询 stamp 和同一组触发原因。这样 RViz 中看到的红点、黄点或风险点能和 planner 日志一一对应。

## 实现阶段建议

### P4-A：静态批量点查询接口

- 新增 planner-facing 查询数据结构和 ROS service。
- 复用当前已经落地的 `UfomapOccupancyState`、`queryNode()`、`queryLocalOccupied()`、`queryNearestOccupied()` 和 query depth 参数，构建点查询和局部 occupied 查询。
- 明确 service 层的 `FREE` / `UNKNOWN` / `OCCUPIED` / `INFLATED_OCCUPIED` / `OUT_OF_MAP` 语义；其中底层状态已有基础，`INFLATED_OCCUPIED` 和 unknown 策略仍需在 P4 定义。
- 返回 `seen_free_evidence`，但不把它当成 `FREE`。
- 加最小单元测试和 service 回调测试。

### P4-B：线段检查和静态膨胀

- 实现批量 `checkLines`。
- 加 `robot_radius` 和 `static_inflation_radius`。
- 先使用采样法，后续再优化为 voxel traversal；当前 `queryNearestOccupied()` 可作为最近障碍证据的第一版近似，但不能替代完整线段碰撞检查。
- 返回首个触发点、最大风险点和触发原因。
- 加 RViz debug marker。

### P4-C：动态时序风险

- 在 `Ldop` 中缓存最近一帧 `DynamicObjectPredictionArray` 快照。
- 实现点和线段的 `time_from_start` 动态风险查询。
- 支持 `max` 和 `1 - product(1 - risk_i)` 两种多目标融合策略。
- 返回触发风险的目标 ID、分支概率、风险时间和风险中心。
- 保持动态风险层独立，不写入 UFOMap。

### P4-D：局部地图快照和 debug 工具

- 实现 `/ldop/query_local_planning_map`。
- 支持静态 occupied / inflated / unknown 和动态风险点分层返回。
- 加最大返回数量和截断标志。
- 配套 RViz debug marker，便于验证 service response。

### P4-E：ESDF 或完整地图副本

只有当规划器确实需要梯度优化或本地高频静态查询时，再补 ESDF 或 `/ldop/ufomap`。

这一步可以二选一，也可以都暂缓：

- ESDF：提供 `/ldop/query_esdf` 和局部 ESDF 可视化；当前 `queryNearestOccupied()` 只能提供离散最近 occupied 近似，不承诺连续 signed distance 或梯度。
- 地图副本：引入 `ufomap_msgs` 或自定义序列化消息，发布完整或局部 UFOMap。

## 验收重点

功能验收：

- 批量查询不能退化为规划器逐点调用 ROS service。
- 静态层和动态层 response 可分离，能单独关闭动态风险。
- 动态目标不会污染 UFOMap 静态地图。
- `/ldop/static_cloud` 和 `/ldop/dynamic_cloud` 仍保持当前帧点云语义，不被改成累计地图。
- 查询结果和 RViz debug marker 在同一 frame / stamp 下可对应。
- unknown 策略、膨胀半径、动态风险阈值都能通过参数或请求字段明确控制。

可解释性验收：

- 点查询能说明 unsafe 来自静态占据、静态膨胀、未知区、地图外还是动态风险。
- 线段查询能返回首个触发点和最大风险点。
- 动态风险能返回触发目标、触发时间和分支概率摘要。
- 局部地图响应被截断时必须显式标记。

通用性验收：

- 一个采样/搜索 planner 能只用点查询和线段检查完成基本碰撞验证。
- 一个 MPC/轨迹优化 planner 能拿到连续动态风险和可选距离信息。
- 一个调试/学习工具能通过局部地图快照复现实验输入。
- 规划器不需要包含 UFOMap 头文件，也不需要理解 `UfomapMapper` 内部结构。

性能验收：

- service 支持批量输入，并返回每批处理数量、截断状态和必要诊断。
- 地图读锁范围可控，不因大规模 service 查询长期阻塞建图线程。
- 动态预测快照查询不阻塞 tracker / predictor 主流程。

## 风险与取舍

| 取舍 | 推荐选择 | 原因 | 后续升级条件 |
|---|---|---|---|
| service 查询 vs 完整地图发布 | 先 service 查询 | 最小依赖、语义稳定、容易融合动态风险 | 规划器需要本地高频静态查询 |
| 采样线段检查 vs voxel traversal | 先采样 | 实现简单、容易验证 | 漏检风险或性能瓶颈出现 |
| 不实现 ESDF vs 第一版 ESDF | 先不强制 ESDF | 保持第一版通用且低风险 | 轨迹优化器明确需要距离/梯度 |
| `max` 风险融合 vs 概率并集融合 | 默认概率并集，可配置 `max` | 并集能表达多目标风险叠加，`max` 更保守且易解释 | 通过 planner 验证选择默认值 |
| unknown 默认安全 vs 默认不安全 | 默认不安全 | 无人机避障更偏安全，探索算法可显式关闭 | 具体探索任务需要 optimistic unknown |

## 一句话备忘

第四阶段给规划器用时，先做 ROG-Map 风格的批量查询接口；UFOMap 继续做 LDOP 的静态地图底座；动态预测只形成独立时序风险层，不写回静态地图；response 保留分层风险和触发证据；RViz 输出用于验证，不作为规划主接口。
